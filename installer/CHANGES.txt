XCL - modified build 14
======================

This is NOT an official XCL release. It is XCL (https://github.com/xcl-dev/xcl, GPL-2.0-only)
built from upstream commit 68a284a (2026-11-25) plus the changes listed below. The complete
source of this build is at https://github.com/theaustinayers/xcl (tag v0.1.0-mod.14, branch
build-14). The licence is in LICENSE.txt, third-party notices in THIRD_PARTY.md.

What changed since build 13
---------------------------
- The 3D world of the tested game is no longer grey: its geometry and its textures are drawn.
  One run of 9 minutes on an RTX 5090 (7.5 of them in the world) ended without a hang, a crash
  or a driver error. It is still NOT PLAYABLE: about 3 frames a second in the world (XCL's work
  on the CPU for each submit is the limit), and the colours are wrong - flattened into a few
  hard bands with a tint. Both are the next thing.
- Textures: the queue's CopyPageMappingsBatchX maps pages into GPU views (on upstream pull
  request #1031), a texture over such pages is read where they are kept and goes up again when
  a mapping under it changes.
- Geometry: the argument pass of a two-pass ExecuteIndirect(DispatchMesh) sets every view it
  declares (a fault of the GPU at the start of the world came from one left unset); depth
  buffers with unordered access get a stencil twin behind XCL_DEPTH_UAV_TWIN=1.
- NVIDIA: the driver keeps the machine code of the pipelines in use in a reserve of 512 MiB.
  This game fills it, and the device is then lost without a message (0x887a0005). The reserve
  can be raised in the driver's profile for xcl.exe: setting 0x001ABC0F (a size in bytes), set
  here to 2048 MiB with a profile tool run as administrator. The run above was made with it.
- A device removal says what the list the GPU was in had left, the state of the device and the
  system's commit; the frame trace names depth buffers and holds a render target only while a
  view holds it (a crash of traced runs).
- Memory: about 31 of 32 GB of video memory and 46 - 54 GB of committed memory were in use in
  the world. A card with less video memory is not expected to get there.

Settings of the run above (environment variables, set them before starting XCL):
  XCL_UMA_WINDOWS=16  XCL_COPY_THREADS=8  XCL_TEXTURE_SAFE_READ=1
  XCL_GFX_PSO_WAIT_MS=100  XCL_HUGE_PSO_CONCURRENCY=3  XCL_PSO_IMAGE_SKIP=1
  XCL_TWO_PASS_MB=4096  XCL_DIRECT_SPLIT_INSTRUCTIONS=0  XCL_NETWORK=0
The shaders were built ahead of the run (xcl shaders <pack> --precompile, see the README);
without that the first minutes in the world stand still while they are compiled.

What this build has that upstream's commit does not
---------------------------------------------------
- Launcher: "Add a game folder..." in the menu (a folder picker).
- Keyboard and mouse: the cursor is taken by a click in the picture and let go by F8, the title
  bar or Alt+Tab; Page Up / Page Down hold the right stick up / down.
- Open upstream pull requests, taken with their authors' commits: #1329, #1850, #1993, #1766,
  #1983, #1599, #929, #2052, #1453, #1422, #605, #1747, #1791, #1358 and #1517, #1792, #1184,
  with fixes on top where they met each other.
- The own changes above (the history of the branch has one commit each), diagnostics
  (XCL_ACTIVITY, XCL_GPU_PROFILE, XCL_LOOK_STATS) and XCL_LOOK_AHEAD=ms (off).
- Installer (installer/xcl.iss): per-user setup that bundles dxcompiler.dll and dxil.dll from
  the Windows SDK next to xcl.exe, option to set XCL_NETWORK=0; build.ps1, BUILDING.md and a
  GitHub Actions workflow that builds the installer from the release tag and attests it.

Several of these are workarounds that keep a title going rather than correct implementations.

What this is and is not
-----------------------
- It contains no game files, keys or shader caches. You need your own unpacked game files.
- Windows 10/11 x64, a Direct3D 12 GPU with Shader Model 6.6 and mesh shaders, and the Xbox
  "Gaming Services" component (System32\xgameruntime.dll) are required.
- XCL is developed on AMD GPUs. On NVIDIA GPUs the driver's shader compiler is slow on XCL's
  translated programs; first runs of a large game can sit on a black window for a long time
  while shaders compile. Compiled shaders are cached, so later runs get further.
- It is unsigned. Windows Defender may flag xcl.exe heuristically (it loads and runs another
  program's code inside itself); it then needs a folder exclusion to run.
- A game runs as native code with no sandbox. Only run game files you trust.
